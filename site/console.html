Integration prototype for the Alembico team

Everything reaches the front desk. Nothing reaches the chart yet.

CareXPS Urgent Care replaced its paper intake form with a tablet flow. A completed form is rendered to PDF and filed into the clinic's OneDrive within a couple of seconds, and staff get a clinical note they can paste into Alembico by hand. The paste is the part we want to remove. This page is the working console that would do it, plus the exact data we would send you.

What we need from you: confirmation of whether Alembico exposes an interface we can post to, and if so, what it expects. Everything else is built. Section “What we need from Alembico” is the short version — four questions.

Every submission below is synthetic test data — invented names, invented health numbers. No real patient information appears anywhere on this page.

Submissions — today

How a submission travels

Five stages, in this order, deliberately. The tablet clears a patient's answers on a 200 and on nothing else, and the desk service returns 200 only once the PDF is confirmed on disk. Stage 05 is the one that does not exist yet.

Patient submits on a tablet

Kiosk tablet on the clinic wifi POSTs the submission JSON to the clinic PC over HTTPS. The tablet holds no credentials for OneDrive or Alembico and stores nothing between patients.

Desk service spools it

The raw submission is written to a local spool and fsynced before any work starts. If the PC loses power mid-render, the form survives and replays on next start.

PDF is rendered and filed

Written atomically into the clinic's synced OneDrive folder as Intake_Last_First_2026-08-29_1042_a7f3c891.pdf. OneDrive handles the rest.

Front desk is notified

The submission appears in the console above with a New chip. Staff currently open the note, select it, and paste it into the patient's Alembico encounter by hand.

Push to Alembico — not built

The clinic PC posts the encounter to Alembico, which files it against the patient matched on their Ontario health number. desk-service/src/alembico.js ships as a documented, disabled stub. It is the only file that changes once you answer.

What we need from Alembico

Public directory listings say Alembico has no API. Alembico's own marketing describes interface-level integrations. Those disagree, so nothing has been guessed at in code — we would rather ship a disabled stub than a wrong assumption. Four questions unblock it.

Question 01 — the blocking one

Is there an interface we can post to at all?

Any of these would work for us, in descending order of preference. We are not asking you to build anything new — we are asking which of these already exists:

  • An HTTP API accepting an encounter or document for a patient
  • An HL7 v2 feed (MDM^T02 or ADT^A04) over MLLP or a file drop
  • A FHIR R4 endpoint — we already produce a conformant bundle, shown in the console above
  • A watched folder Alembico ingests from, with a filename or sidecar convention
  • Nothing — in which case staff keep pasting, and we would like that confirmed in writing so we stop asking
Question 02 — patient matching

How does Alembico identify which chart this belongs to?

Every submission carries an Ontario health number, normalised to ten digits plus an optional two-letter version code, separators stripped, upper-cased — 4821567390AB. Does Alembico accept that as a lookup key, or does it need your own internal patient ID? And what should happen when the number matches nobody: create the chart, or hold the encounter for staff to reconcile?

Roughly one submission in eight is a first-time patient with no chart yet, so the "no match" path is not an edge case for us.

Question 03 — payload shape

What does the encounter body look like?

We can send any of four representations of the same submission, all generated from one canonical object so they cannot drift apart: a plain-text clinical note, a flat CSV row, the full JSON, or a FHIR R4 bundle. All four are in the console above — open a submission and switch tabs. Tell us which you want and we will send that one.

Also: can we attach the signed PDF to the encounter, or does the note have to carry everything?

Question 04 — credentials and environment

How do we authenticate, and is there a test environment?

Bearer token, mutual TLS, IP allowlist, something else? The credential will live on the clinic PC only — never on a tablet, which is a screen in a public room. We would also like a non-production target to send test submissions to before anything touches a real chart.

Matching on the health number

The suggestion was to key on the health card number, possibly through the filename. That works, with one caveat worth raising before it gets built.

A health number in a filename is health information in a place that is not protected like health information. Filenames travel further than file contents: they appear in OneDrive sync logs, backup indexes, folder listings, and any support ticket where someone pastes a directory. The current build deliberately keeps identifiers out of filenames and logs for exactly this reason.

So the preference is to match on a field in the payload rather than the filename. If a watched folder is the only integration Alembico offers, a sidecar .json next to each PDF carries the number without putting it in the name. If the filename genuinely has to carry it, we will build that — it is the clinic's call, not ours — but it should be a decision someone made rather than one that happened.

One canonical submission object. The PDF, the note, the CSV and the FHIR bundle are all derived from it, so they can never disagree. Two pathways produce two shapes, and the difference matters for anything consuming this.

Things worth knowing before you read the data

The health card photo is never kept

A patient can photograph the front of their card, but the image is discarded immediately and the number is typed by hand. An OCR guess written into a chart as a health number is worse than no number at all — it silently points at somebody else.

This is patient-entered and unverified

Nobody at the clinic has checked any of it when it reaches you. Every export carries that statement in its footer. If Alembico distinguishes verified from self-reported data, the whole submission belongs in the self-reported category.

Delivery is at-least-once, so treat meta.id as an idempotency key

If the PDF files successfully but the push to Alembico fails, the submission sits in the queue and retries. The same meta.id arriving twice must not produce two encounters.

Nothing here is stored longer than it needs to be

The tablet keeps no localStorage, sessionStorage, IndexedDB or cookies — state lives in memory for one session and the page hard-reloads afterwards. Logs record a reference and an outcome, never field values. The clinic's OneDrive folder is the system of record until Alembico becomes one.
